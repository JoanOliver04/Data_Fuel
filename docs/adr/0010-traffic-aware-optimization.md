# 0010 — Traffic-aware multi-objective optimization engine

- **Status:** Accepted
- **Date:** 2026-05-29
- **Deciders:** Data Fuel maintainers

## Context

Until now Data Fuel ranked stations by a single objective: total refuelling
cost `Cᵢ = (V · Pᵢ) + (Dᵢ · K)` (fuel + a flat per-km travel cost). That is a
solid *price* answer but a weak *decision* answer. The cheapest pump can be 18 km
away down a congested road; a station 3 €-cents dearer but 3 km away with no
traffic is usually the better real-world choice once the drive — and the time it
consumes — is priced in.

We already had the raw ingredients: [ADR 0007](0007-tomtom-routing-provider.md)
added TomTom Matrix Routing v2, which returns driving distance, **ETA** and
**`traffic_delay_seconds`** (delay versus free-flow); the cost calculator already
carries these onto every `StationCost`. What was missing was a way to *combine*
them into one comparable decision, and a way to let the user say what they care
about.

Hard constraints (non-negotiable): keep the Random Forest recommender, the
TomTom / ORS / haversine providers and the existing `/recommendations` contract;
existing tests must pass; `mypy --strict` and `ruff` must pass; the new
behaviour must be **additive and backwards compatible**.

## Decision

Add an `app/services/optimization/` layer that scores each candidate on a single
**euro-denominated** objective and re-ranks by it:

```
score = w_fuel·fuel_cost + w_distance·travel_cost
      + w_time·time_cost  + w_traffic·traffic_penalty          (lower is better)

time_cost       = eta_minutes × (TIME_COST_PER_HOUR / 60)      # default 15 €/h
traffic_penalty = (traffic_delay_seconds / 60) × FACTOR        # default 0.25 €/min
```

Weights come from a user-selectable `OptimizationProfile`
(CHEAPEST / BALANCED / FASTEST / COMMUTER), each summing to 1.0. The score is
exposed via an **optional** `optimization_profile` query param on
`GET /recommendations` plus a `GET /analytics/optimization-summary` aggregate
endpoint. Rationale text is **deterministic and template-based** (es / en), never
generated by an LLM.

### Why multi-objective optimization

Choosing a refuel stop is a textbook multi-criteria decision: the criteria
(money, distance, time, congestion) conflict and trade off. We use **weighted-sum
scalarization** — collapse the criteria into one scalar via a convex combination
of weights. It is the simplest scalarization that is transparent (the user sees
exactly how much each criterion counts), cheap (one dot product per station, no
solver) and, crucially here, *interpretable in euros*. The alternative,
returning a Pareto front of non-dominated stations, is academically purer but
hands the user a set rather than a ranked list — wrong for a "show me the best
pump" UX. Scalarization with named presets keeps the decision a single ordered
list while still exposing the trade-off knob.

### Why time has economic value

The classic cost formula implicitly prices time at **zero**, which is why it
over-weights distant cheap stations. Transport economics routinely monetises
travel time (the "value of travel time savings"); we adopt a simple, explicit
`TIME_COST_PER_HOUR` (default 15 €/h ≈ a conservative net hourly wage) and
convert ETA minutes to euros. This is a *preference parameter*, not a physical
constant — hence configurable, and a future per-user value is an explicit
extension hook (`weights_override`).

### Why TomTom traffic data improves recommendations

Free-flow distance/ETA misrepresents the real cost of a congested route. TomTom's
`traffic_delay_seconds` is the live delay versus free-flow; pricing it
(`TRAFFIC_PENALTY_FACTOR`) lets the optimizer *automatically* avoid jammed routes
without any hand-tuned rules. The data already flows through the routing layer,
so this is essentially free signal we were previously discarding.

## Trade-offs

- **Scalarization hides the Pareto front.** Two stations with very different
  profiles can score similarly; we surface the full per-component breakdown on
  each card so the user can see *why*, mitigating the opacity of a single number.
- **Weights and the €/h, €/min constants are judgement calls.** They are
  centralised in `Settings` and the profile table, documented, and unit-tested,
  so they are easy to tune and never hidden in code.
- **No ETA in straight-line modes.** Haversine and ORS expose no traffic, and
  haversine no duration. The engine degrades gracefully: `time_cost` and
  `traffic_penalty` are 0 and the score collapses to weighted fuel + travel cost —
  identical relative ordering to the legacy behaviour, never an error.
- **Backwards compatibility beat the "default = BALANCED" spec.** Defaulting the
  raw endpoint to BALANCED would have re-ordered every existing client and broken
  the ranking tests. We made the param optional (legacy ranking when omitted) and
  put the BALANCED default in the **frontend**. The constraint won, as required.

## Performance

One `evaluate()` per station is a handful of float multiplies — negligible next
to the routing matrix call that already dominates a driving-mode request. No new
network calls, no model load, no GPU. The analytics summary bounds its candidate
set (`_SUMMARY_CANDIDATE_LIMIT = 50`) and is served through the same short-TTL
cache as the other read endpoints. Added latency on the recommendation path is
sub-millisecond.

## Alternatives considered

- **Pareto-optimal front (skyline).** Returns non-dominated stations only.
  Mathematically elegant, poor UX for a ranked "best pump" list, and harder to
  explain to a non-technical user. Rejected for the primary flow.
- **Learning-to-rank / a second ML model.** Could learn weights from behaviour,
  but we have no click/choice telemetry yet, it would be a black box on top of a
  black box (fighting the XAI story of ADR 0009), and it violates the
  determinism we wanted. Rejected; revisit once choice data exists.
- **LLM-generated rationale.** Rejected for the same reasons as ADR 0009:
  hallucination risk, non-determinism, latency and cost. The explainer is curated
  templates.
- **Normalising components to [0,1] before weighting.** Would make weights pure
  preferences decoupled from scale, but loses the "score is a euro figure" property
  that makes the breakdown directly legible. Rejected in favour of keeping euros.

## Future extensions (hooks only, not implemented)

`weights_for(profile, override)` and the profile table leave seams for:
personalized time value, company-fleet cost models, EV charging-aware scoring,
full route / multi-stop optimization, and dynamic fuel planning. None are built;
only the extension points exist.
